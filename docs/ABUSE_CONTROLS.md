# Abuse controls and staging rollout

## Controls checked into the app

- Firebase ID tokens establish learner identity; admin routes also check the current custom claim. Hosted custom APIs verify the `X-Firebase-AppCheck` token with Firebase Admin and require the configured Firebase Web App ID, not merely any app in the project. The keyless demo bypasses hosted attestation by design.
- Gemini admission checks the learner and workspace ceilings atomically. The workspace defaults are 200 admitted learner requests per UTC day and 20 per minute, configurable with `AI_PROJECT_DAILY_LIMIT` and `AI_PROJECT_PER_MINUTE`. `0` pauses model work at that scope. Tune them to the provider project's actual limits; one admission can include a query embedding, chat, and bounded SDK retry. The trusted CLI indexer is outside the learner admission budget. Quota scopes are shared by app instances pointing to the same Firestore project. These counters are not a substitute for provider-side limits or billing alerts.
- Curriculum imports use both per-admin (4/minute, 20/day) and workspace (8/minute, 60/day) limits. They do not use Gemini allocation. The public emulator preview has a small instance-local auth/registration ceiling and disables its custom-token exchange; it is for disposable SAMPLE accounts and must never be connected to production services.
- Redacted events: `rate_limited` (scope-specific code), `app_check` (outcome), `account_signal` (profile created or public-demo Auth signal), `admin_import` (published or unchanged), and model outcome/usage. No app events above log identities, raw IPs, prompts, or tokens. A profile-creation signal is **not** a count of all Firebase signups.

## Authorized hosted staging steps (not executed here)

1. Register the Firebase Web app in [Firebase App Check with reCAPTCHA Enterprise](https://firebase.google.com/docs/app-check/web/recaptcha-enterprise-provider) for the intended staging hostname. Set `NEXT_PUBLIC_FIREBASE_APP_CHECK_SITE_KEY` at build and runtime and the matching `NEXT_PUBLIC_FIREBASE_APP_ID`. The site key is public, not a server secret. Do not put a debug token or production credential in a build, log, or repository.
2. Set `APP_CHECK_MODE=observe` in staging while confirming a real browser sends an attestation and `app_check` reports `verified`. Change to `required` (the hosted default) after baseline verification. Test successful authenticated traffic, absent/invalid/wrong-app attestation, and sign-out. Observe mode logs mismatches but does not block. The custom-resource approach follows [Firebase's server verification guide](https://firebase.google.com/docs/app-check/custom-resource-backend). It does not perform one-time token consumption; normal App Check tokens are reusable, so keep the other controls enabled.
3. Configure [Vercel WAF rate limiting](https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting) in the assigned project, using the platform's IP key, not a client-supplied forwarding header. Start with an observed rule for `/api/*` (except `/api/health`); prioritize inference and upload writes if rule counts are limited. Review shared corporate/school NATs before enabling 429 enforcement. If deploying Docker elsewhere, put an equivalent rule at a trusted reverse proxy and restrict bypass of the origin. Firebase's hosted Auth endpoints are separate from the app's WAF.
4. Use [Identity Platform activity logging](https://docs.cloud.google.com/identity-platform/docs/activity-logging) where available. Track `AuthenticationService.SignUp` and `SignInWithIdp`, broken down by outcome; IdP sign-ins are not synonymous with new accounts. Review real registrations with authorized console metrics. Set aggregated alerts on signup surges, unusual failed auth and App Check rates, provider/ordinary/admin 429s, and elevated provider errors/consumption. Keep access and retention limited. Confirm receipt of an alert during a controlled staging test before rollout.

Cloud App Check exchange, edge controls, signup monitoring, and dashboards/alerts are **NOT RUN / not configured here**. The policy unit tests use an injected verifier, and the service-cap HTTP/Firestore gates run on emulators; neither proves hosted attestation or edge behavior.
